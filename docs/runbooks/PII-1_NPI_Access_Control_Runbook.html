PII-1 — NPI Access-Control Runbook

Layered access controls for NPI data in the SageMaker Unified Studio sandbox

Control: PII-1 · Data Handling & Reg S-P Applies to: Track A (V1) sandbox Version: 1.4 — updated 3 Oct 2026 (ETL build-pass gotchas; network posture noted for Track B) Domain: IAM-based, us-east-2

Purpose & principle

This runbook stands up access controls for a sandbox that touches NPI. The principle is defense in depth: no single control is enough. Layer all five — a gate at the door, tags on the data, scoped policies, an isolated project, and a manual datashare gate. The core is LF-Tags + identity; the rest tie it together with least privilege.

DO IT IN ORDER, STARTING AT STEP 0. The first build pass lost time to region mismatches, a permissions-boundary deny, and blueprints that would not disable. Step 0 exists so those are settled before any control is configured. Do not load NPI until Step 5 and the verification checklist are complete.

  • The pilot IAM group sandbox_datashare_pilot_group — drives S3 bucket access and SMUS membership. Not usable as a Lake Formation principal (LF grants stay per user).
  • The test bucket sandbox-datashare-test-bucket-test, Block Public Access enabled (all four settings).
  • A domain-admin session — not a project-user role. See Step 0 for why.
  • Admin access to Lake Formation, IAM, and the SMUS domain, all in us-east-2.
  • The NPI datasets/tables identified, ready to tag.

Step 0 — Environment prerequisites (new in v1.1)

0

Get region, identity, and session right before touching controls

Prevents the three failures that stalled the first pass

Do this:

  1. Co-locate the domain with the data. The SMUS domain must be in the same region as S3, Redshift, and Glue — us-east-2. Region is fixed at domain creation and cannot be changed; cross-region breaks Lake Formation permissioning and adds transfer cost. A domain created in the wrong region is deleted and recreated, not fixed. Current domain: dzd-ccfyu0e7eahzhl, us-east-2.
  2. Check IAM Identity Center before building. Identity Center has one home region per organization. If it is unset or in a different region than the domain, the domain cannot add users (fails on datazone:CreateGroupProfile). This domain is IAM-based, so Identity Center is deferred to Track B — but confirm its region now so Track B's new domain lands correctly.
  3. Use a domain-admin session, not the project execution role. AmazonSageMakerAdminIAMExecutionRole_1 carries the SageMakerStudioProjectUserRolePermissionsBoundary, which explicitly denies domain-level actions like adding users. Attaching a policy does not help — the boundary wins. Do not remove the boundary; log in with a proper admin identity instead.
  4. Notify Security / Arctic Wolf first. Domain creation spawns new IAM roles, an S3 bucket, and Glue/Lake Formation activity — all of which alert. Give a heads-up, document the expected roles, and log it as a planned change before clicking Create.
  5. Leave "Make your data discoverable" unchecked at domain creation. NPI must not be auto-catalogued before LF-Tag policies exist.
  6. Record the portal URL (form https://dzd-<id>.sagemaker.us-east-2.on.aws). SMUS-created domains are locked to the portal; the classic SageMaker console redirects with a validation error. Users cannot reach the project without this link.
Confirm: domain and data are both in us-east-2; you are working from an admin session; Security has been notified; portal URL captured. Domain creation itself is free — costs start when Spaces run or data is queried.

The five layers

1

Identity — who can enter

Controls: who can log into the domain

Do this:

  • This domain is IAM-based, so pilot users are individual IAM users, granted per person. Identity Center groups come with the new domain in Track B.
  • Before adding a user, attach SageMakerStudioUserIamConsolePolicy to the execution role. It is a custom policy that already exists in the account — attach it, do not recreate it.
  • Assign users with SageMakerStudioUserIAMDefaultExecutionPolicy. Do not use SageMakerStudioUserIAMPermissiveExecutionPolicy — it grants broad data access.
Open item — Track B, raise with Compliance. All pilot users are on SageMakerStudioUserIAMDefaultExecutionPolicy, consistent with the approved model, and none are admitted to the SMUS domain yet. Separately, the group sandbox_datashare_pilot_group carries SageMakerStudioAdminIAMDefaultExecutionPolicy — a domain-admin policy attached at group level. That is inert until members are admitted to the domain, but once they are, the group grant would layer admin capability on top of their user policy. Accepted for Track A given the sandbox and known membership; carried to Track B as a Compliance review item with the Identity Center cutover, where the group grant should be reset to the User policy and admin reserved for the admin identity.
  • Phase 1: iam-bolu-mobolaji (provisioning only) and iam-sandbox-bolu (working identity). Phase 2: the remaining four, after the environment is verified.
  • Membership is two steps, in two different UIs. First add the user to the domain in the Amazon DataZone console (AWS Management Console → DataZone → Domains → dzd-ccfyu0e7eahzhl) — not the Unified Studio portal. Only once they are a domain member can they be added to the project, and that second step is done inside Unified Studio. Adding to the project first, or from the wrong UI, fails or the user does not appear as a candidate.
Confirm: only phase-1 users exist; default (not permissive) policy attached; console policy attached to the execution role. This gate alone does not restrict data — continue to Step 2.
2

Lake Formation LF-Tags — what data they can see

Controls: which data assets are queryable · most critical layer

Do this, in four parts:

  1. Get the permission first. Creating a tag as a non-admin fails with Insufficient Lake Formation permission(s): Required Create LF Tag on Catalog. Register iam-bolu-mobolaji as Data Lake Administrator under Lake Formation → Administration (or Permissions) → Administrative roles and tasks. On a never-configured account this is the welcome-screen "first data lake administrator" field. An IAM policy alone is not sufficient — the console registration is required as well.
  2. Create the tags. Permissions → LF-Tags and permissions → LF-Tags → Add LF-Tag: data_class (npi, standard), environment (pilot, prod), sensitivity (restricted, internal, public).
  3. Assign at the database level. Data Catalog → Databases → NPI database → Actions → Edit LF-Tags → data_class=npi, sensitivity=restricted. Tables and columns inherit.
  4. Grant, then revoke. Permissions → Data lake permissions → Grant. Principal type IAM users and roles (IAM user groups are not supported as LF principals). Resources matched by LF-Tags: data_class=npi AND sensitivity=restricted. Database: Describe. Table: Select, Describe. Then revoke any existing SELECT to IAMAllowedPrincipals or broad roles on the NPI database — they bypass the tag policy entirely.
Confirm: iam-sandbox-bolu can query tagged tables; a non-pilot principal is denied; no IAMAllowedPrincipals grants remain on the NPI database. Enforcement holds at query time across Athena, Redshift, and Glue.
3

IAM policies with conditions — how they can act

Controls: which actions and resources are permitted

Attach to the project role, not the admin policy. The scoped policy goes on the auto-created project role (AmazonSageMakerStudio-<project-id>-ProjectRole), found under the project's settings in the SMUS portal. Never attach it to SageMakerStudioAdminIAMDefaultExecutionPolicy.

Do this:

  1. Verify the boundary first. Open the project role in IAM → Permissions → Permissions boundary. SageMakerStudioProjectUserRolePermissionsBoundary must be listed. If it is absent, stop — the project was not provisioned correctly. The boundary caps what the role can ever do; the inline policy cannot exceed it.
  2. Attach the scoped inline policy (Add permissions → Create inline policy → JSON). Name it NPI-Pilot-ProjectRole-ScopedPolicy. Replace every placeholder — region is us-east-2:
{ "Version": "2012-10-17", "Statement": [
  { "Sid": "RestrictDataZoneToPilotDomainAndProject", "Effect": "Allow",
    "Action": ["datazone:CreateSubscriptionRequest","datazone:GetSubscription",
               "datazone:ListSubscriptions","datazone:DeleteSubscriptionRequest"],
    "Resource": ["arn:aws:datazone:us-east-2:<account-id>:domain/<domain-id>",
                 "arn:aws:datazone:us-east-2:<account-id>:domain/<domain-id>/project/<project-id>"] },
  { "Sid": "RestrictS3ToNPIPilotBucket", "Effect": "Allow",
    "Action": ["s3:GetObject","s3:PutObject","s3:ListBucket"],
    "Resource": ["arn:aws:s3:::<npi-pilot-bucket>","arn:aws:s3:::<npi-pilot-bucket>/*"] },
  { "Sid": "RestrictAthenaToNPIWorkgroup", "Effect": "Allow",
    "Action": ["athena:StartQueryExecution","athena:GetQueryExecution","athena:GetQueryResults"],
    "Resource": "arn:aws:athena:us-east-2:<account-id>:workgroup/<npi-workgroup>" },

  1. Space tagging is deferred for the pilot. The aws:ResourceTag condition on SageMaker Spaces only works if Spaces are tagged, and tagging them from the console is not possible for SMUS domains (Spaces is greyed out in the SageMaker AI console; they live in the portal). It requires CLI: aws sagemaker list-spaces --domain-id dzd-… --region us-east-2, then aws sagemaker add-tags on the space ARN. Note the domain ID uses the dzd- prefix (DataZone), not d-. For five users, Layers 1–2 are the load-bearing controls; add the space condition when the pilot is stable.
  2. Verify with the IAM Policy Simulator. Select the project role. s3:GetObject on a non-pilot bucket → denied; on the pilot bucket → allowed; datazone:CreateSubscriptionRequest on another domain ARN → denied.
Confirm: boundary present; inline policy attached to the project role; simulator results as above.

Test bucket access — decided model (Option A)

Bucket: sandbox-datashare-test-bucket-test · where NPI first persists

Decision for Track A: no bucket-policy Deny. Access is controlled by Block Public Access + a group Allow policy, so membership changes touch the group only, never the bucket.

  1. Block Public Access — all four settings enabled on the bucket (done).
  2. Group Allow policy — inline policy SandboxDataSharePilotBucketAccess on sandbox_datashare_pilot_group: s3:GetObject, s3:PutObject, s3:DeleteObject, s3:ListBucket on the bucket and its objects (done).
  3. Bucket policy left empty. Anyone not in the group has no Allow and cannot reach the bucket.
Why not a Deny-except-named-roles bucket policy? S3 bucket policies cannot reference IAM groups, and an explicit Deny with ArnNotLike beats any group Allow — so group members get blocked unless every user ARN is listed and kept in sync. Option A was chosen to avoid that. Its guarantee depends on no broad S3 Allow existing elsewhere (e.g. an AdministratorAccess group — iam-bolu-mobolaji sits in one). Inventory broad grants before phase 2. If a Deny is later wanted, use a principal-tag condition (aws:PrincipalTag/PilotAccess) rather than ARN lists.
Consider trimming write/delete for non-builders. The group policy grants PutObject and DeleteObject to every pilot member on the NPI snapshot bucket. Only the Glue job and the builder need to write; analysts and oversight roles need read. Consider a read-only variant for phase-2 users.
Confirm: Block Public Access on; group policy attached; bucket policy empty; a non-group principal is denied; broad-Allow inventory reviewed.

SMUS project isolation — the sandbox boundary

Controls: the environment boundary

Role tags do not disable blueprints. Setting Enable…Permissions tags on the execution role does not retroactively turn off blueprints that were auto-enabled at domain creation. Blueprints must be disabled by hand in the domain's Blueprints tab — both pages of it.

Do this:

  1. Use the existing Admin project — do not create another (fails with Admin project already exists). Create a dedicated pilot project for the sandbox; add only pilot users.
  2. To add a member to the project: (a) add them to the domain in the Amazon DataZone console (AWS Management Console → DataZone → Domains → dzd-ccfyu0e7eahzhl → Members); (b) then add them to the project from inside the Unified Studio portal. Domain membership is the prerequisite — a user not yet on the domain cannot be added to the project.
  3. In the DataZone console → the domain → Blueprints tab (…/datazone/home?region=us-east-2#/domains/dzd-ccfyu0e7eahzhl/capabilityblueprints), select each unneeded blueprint and Disable, one at a time, then check page 2:

5

Datashare subscription approval — the Track A datashare path

Controls: the manual gate for datashare access · deferred until S3 versioning is enabled

Sequence (do in order once versioning is on):

  1. Enable S3 versioning on sandbox-datashare-test-bucket-test → Properties → Bucket Versioning → Enable.
  2. Publish the asset in the DataZone portal: Projects → pilot project → Publish data → source S3 → the bucket → metadata → Publish.
  3. Set the approver on the published asset: Data Catalog → asset → Subscription tab → Edit → Approval type Manual → approver. Alternatively set once at project level (Projects → project → Settings → Subscription policy) so every asset inherits it.
  4. Approver: B. Mobolaji per the sandbox decision. Q suggested routing to sandbox_datashare_pilot_group instead — a group approver avoids a single-person bottleneck if the pilot grows; decide before phase 2.
  5. Revisions: each new S3 upload creates a version; publish a new asset revision in the portal, which raises a fresh subscription request for approval. Grants are on views over the shared tables, not the tables directly.
  6. Optional, V1.5: EventBridge rule on DataZone Asset Published → SNS to pilot emails. Alerting is out of scope for Track A; note it for the monitoring phase.
Confirm: versioning on; asset published; approval type Manual with a named approver; a test subscription request requires approval; grants on views only.

Verification checklist (PII-1 pass criteria)

  • ☐ Domain and data both in us-east-2; portal URL recorded; Security notified of domain creation.
  • ☐ Phase-1 identities only; users on the User (not permissive) execution policy; console policy attached; no users admitted to the domain until Layers 2–4 are verified. (Group-level Admin policy noted — Track B Compliance item.)
  • ☐ Data lake administrator registered; LF-Tags created; NPI database tagged data_class=npi, sensitivity=restricted.
  • ☐ Per-user LF-Tag grants (SELECT / DESCRIBE) issued; no IAMAllowedPrincipals grants remain on the NPI database.
  • ☐ Permissions boundary present on the project role; scoped inline policy attached; Policy Simulator results as specified.
  • ☐ Test bucket: Block Public Access on; SandboxDataSharePilotBucketAccess on the group; bucket policy empty; broad-Allow inventory reviewed; non-group principal denied.
  • ☐ Blueprints reduced to Tooling, LakeHouseDatabase, LakehouseCatalog (Bedrock/ML reconciled against the approval sheet).
  • ☐ Dedicated pilot project; pilot members only — each added to the domain (DataZone console) before the project (Unified Studio).
  • ☐ S3 versioning on; asset published; subscriptions on Manual approval with a named approver; grants on views only.
  • ☐ Athena-results prefix restricted to the same group.
